# Board data schema

A board is one HTML page plus its artifact database. The page code is generic; everything project-specific lives in these files, which the skill writes into the board folder and then seeds into the database.

```
<board_dir>/
  config.json          # values baked into the page (not in the database)
  meta/plan.json       # -> database doc meta/plan
  meta/rules.json      # -> database doc meta/rules
  tasks/<ID>.json      # -> database docs tasks/<ID>, one per task
  log/<id>.json        # -> database docs log/<id> (check_board.py writes the seed entry)
  board.html           # generated by build_page.py
  seed_batches.json    # generated by check_board.py
```

## Contents

- config.json
- meta/plan
- meta/rules
- tasks/<ID>
- log/<id>
- Who writes what after seeding

## config.json

Only used by `build_page.py`. Agents read these values from the page's "For agents" section, so they must be right.

```json
{
  "title": "Payments Rewrite Build",
  "eyebrow": "payments-rewrite · build coordination",
  "plan_title": "Payments Rewrite Plan",
  "plan_url": "https://claude.ai/artifact/AbC123",
  "plan_read_how": "with the Claude Docs connector",
  "board_url": "",
  "branch_example": "pr-104-refund-endpoint",
  "commit_example": "[PR-104] Add refund endpoint",
  "example_id": "PR-104"
}
```

- `plan_read_how`: how an agent reads the plan, written to follow "Read the <plan_title> (<plan_url>)". Examples: `with the Claude Docs connector`, `with the Artifact tool`, `from docs/plan.md in the repo`, `with the Atlassian connector`.
- `board_url`: empty until the first publish returns a URL. Use the bare `https://claude.ai/artifact/<id>` form. Never include a `?sk=` share key: the page is readable by everyone it's shared with, and the key grants access.
- Use a real task ID from this board for `example_id`, and make the branch and commit examples match it.

## meta/plan

```json
{
  "title": "Payments Rewrite Build",
  "source_title": "Payments Rewrite Plan",
  "source_url": "https://claude.ai/artifact/AbC123",
  "source_rev": 14,
  "seeded": "2026-11-16",
  "seeded_by": "jake",
  "id_prefix": "PR",
  "start": "2026-11-16",
  "end": "2027-01-29",
  "people": [
    {"id": "mike", "label": "Mike"},
    {"id": "jake", "label": "Jake"}
  ],
  "lanes": [
    {"id": "mike", "label": "Mike", "about": "API, data model, migrations"},
    {"id": "jake", "label": "Jake", "about": "Clients, outputs, CI"},
    {"id": "both", "label": "Mike + Jake", "about": "Decisions, first end-to-end run, go-live", "shared": true}
  ],
  "phases": [
    {"id": "D",  "label": "Decisions", "done_when": "Each decision recorded before the task it gates starts."},
    {"id": "P0", "label": "Phase 0 · Access", "done_when": "A CI job can check out both repos and post to the test channel."}
  ],
  "milestones": [
    {"id": "M0", "label": "Access works", "date": "2026-11-19", "task": "PR-008"}
  ],
  "holidays": [{"date": "2026-11-26", "label": "Thanksgiving"}],
  "timeline_note": "Deploys freeze on Fridays."
}
```

- `people`: who claims tasks. Their `id` goes into `owner` and `log.lane`. Use short lowercase ids.
- `lanes`: the proposed split of the work. A person's own lane uses the same id as the person. A lane with `"shared": true` is joint work that either person can claim. A single-person board has one person and one lane.
- `phases`: ordered. The label shows on the graph and timeline; `" · "` in a label wraps onto two lines in the graph. `done_when` must describe something you can demonstrate, not "phase complete".
- `milestones`: each milestone is gated by exactly one task. The milestone is met when that task is done.
- `source_rev`: the plan's version number if it has one, otherwise omit it. The header shows "Plan seeded <date> from plan revision <n>".
- `timeline_note`: optional sentence shown under the timeline.

## meta/rules

Cross-cutting decisions that apply to every task: merge policy, branch and commit format, environments that are off-limits, how secrets are handled, temporary exceptions. Agents read this before claiming work, and the page shows it in "Project rules".

```json
{
  "items": [
    {"id": "R1", "text": "Open one PR per task. Merge your own PR (squash) once CI is green and every Definition of done item is met. Never push to `main` directly.", "by": "mike", "date": "2026-11-16", "revisit": "when the build is complete"},
    {"id": "R2", "text": "No live environments: never connect to staging or production, even to read.", "by": "jake", "date": "2026-11-16"}
  ]
}
```

Why this exists: on the first board a person changed a repo setting on purpose for the build period, but the record of that sat in one task's amendments. Another agent "fixed" it back, then had to revert. A rule here is visible on every task.

Backticks in `text` render as code on the page.

## tasks/<ID>

```json
{
  "id": "PR-104",
  "title": "Add the refund endpoint",
  "short": "Refund endpoint",
  "phase": "P1",
  "lane": "mike",
  "deps": ["PR-101", "PR-D2"],
  "est_days": 1.5,
  "start": "2026-11-20",
  "end": "2026-11-21",
  "needs": "Decision PR-D2 recorded",
  "source": "Plan › API › Refunds",
  "status": "todo",
  "owner": null,
  "spec": {
    "what": [
      "Add `POST /refunds` that takes `paymentId` and `amountCents`.",
      "Reject refunds larger than the remaining captured amount with a 422."
    ],
    "not": [
      "Partial-capture support (PR-107).",
      "The client UI for refunds (PR-203)."
    ],
    "dod": [
      "Request spec covers success, over-refund (422) and unknown payment (404); `bundle exec rspec spec/requests/refunds_spec.rb` passes.",
      "PR merged with green CI."
    ],
    "where": ["app/controllers/refunds_controller.rb", "config/routes.rb"],
    "brief": "Refunds go through the provider adapter, never the provider SDK directly, so PR-107 can add partial captures without touching this endpoint.\n\nIf the provider's refund call times out, record the refund as `pending` and let the reconciliation job (PR-110) settle it. Don't retry inline: a retry can double-refund."
  },
  "impl": {"summary": "", "files": [], "decisions": [], "verification": [], "open_questions": []},
  "prs": [],
  "amendments": [],
  "branch": null,
  "jira": null,
  "blocked_reason": null,
  "decision": null,
  "started_at": null,
  "done_at": null,
  "updated_at": null
}
```

| Field | Rules |
|---|---|
| `id` | `<prefix>-<number>`, stable forever. Number by phase: `-001`… for phase 0, `-101`… for phase 1, and so on. Decision tasks are `<prefix>-D1`, `<prefix>-D2`. Leave gaps so you can add tasks later without renumbering. |
| `title` | An imperative sentence: what gets done. |
| `short` | 23 characters or fewer; it labels the graph node and timeline row. |
| `phase`, `lane` | Must exist in `meta/plan`. |
| `deps` | IDs of tasks that must be **done** before this one can start. List only direct, hard dependencies. |
| `est_days` | Working days, in quarter-day steps. It drives the critical path. |
| `start`, `end` | Planned dates. A task should start on or after every dependency's `end`. |
| `needs` | An outside dependency, such as a role, an access grant, hardware or a decision. Omit if there is none. Start decision tasks with "Decision". |
| `source` | The plan section the task comes from, for traceability. |
| `status` | Seed as `todo`. A task is shown as "Ready" when it's `todo` and all its deps are `done`; that's computed, never stored. |
| `spec.what` | Imperative steps. Backticks render as code. |
| `spec.not` | The nearby work this task must not do. Name the task that does it. |
| `spec.dod` | Checks someone else could repeat: a command and its expected result, an observable behaviour, a merged PR. |
| `spec.where` | Repo-relative paths, or a UI or console location. |
| `spec.brief` | The why, constraints, traps and fallbacks. A blank line separates paragraphs, and lines starting with `- ` become lists. |

Seed the remaining fields (`impl`, `prs`, `amendments` and the nulls) exactly as shown, so agents find them where the page's instructions say they are.

## log/<id>

```json
{"ts": "2026-11-17T14:02:00Z", "task": "PR-104", "lane": "mike", "kind": "claim", "text": "Started the refund endpoint."}
```

- The id is `<YYYYMMDDTHHMMSSZ>-<task>-<person>`. The page adds a random suffix to entries it writes, to avoid collisions.
- `task` may be `null` for plan-level entries.
- `kind` is one of: claim, progress, review, done, blocked, unblocked, note, decision, amendment, replan or handoff.

## Who writes what after seeding

| Document | Agents | People (directly or through their agent) |
|---|---|---|
| `tasks/*`: status, owner, impl, prs, dates, branch, jira, blocked_reason, decision | `update` with `if_version` | Same, or with the page's Save control |
| `tasks/*`: id, deps, spec, lane, phase | Never. Append to `amendments` instead | `update` with `if_version`, plus a `replan` or `amendment` log entry |
| `meta/plan`, `meta/rules` | Only when their person says so | `update` with `if_version`, plus a `decision` log entry |
| `log/*` | `set` new entries only | Same |
